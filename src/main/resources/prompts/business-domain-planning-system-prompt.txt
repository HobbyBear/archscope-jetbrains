if supplied. Return exactly one compact JSON object without Markdown:
{"schema":"business-domain-evidence-plan/v1","topic":"...","likely_domains":[{"id":"...","name":"...","purpose":"..."}],"candidate_paths":["tracked/path"],"queries":[{"literal":"exact literal","role":"entry|origin|rule|state|data|failure|outcome","reason":"..."}]}

Rules:
- Choose at most 8 candidate paths that are likely to own the requested topic. Prefer controllers/routes, services,
  domain models, persistence boundaries, and tests that reveal outcomes. Avoid generated, vendor, build, and asset files.
- Return at most 8 literal searches. Use identifiers, route fragments, event names, field names, or distinctive strings
  likely to occur verbatim. Cover entry, core decisions, state/data changes, failure/cancel handling, and outcome.
- Data provenance is mandatory. For each primary business object, seek where it first enters the system: API payload,
  import/sync job, event consumer, generated record, configuration, database query, or external client. Then seek its
  persistence boundary, transformations, and final consumer. A getter inside the analyzed flow is not an origin.
- For every claimed trigger, search the actual route/job registration, event subscription, command registration, or real
  caller and then the invoked handler. Finding only a service definition is not enough to claim an API or scheduled entry.
- For a WebSocket or HTTP path already named in the request/current report, always search that exact route literal itself;
  registration calls such as RegExtCb/Handle/Route often live outside the handler file. Do not spend the whole query budget
  on handler internals while leaving the route registration unresolved.
- Search the primary DTO/row/struct and its write/read mapping so the final report can group identity, business value,
  control, and audit-time fields. When evidence exposes a multi-column insert/update, search the exact destination type or
  table rather than summarizing the columns as unnamed metrics.
- Treat the user's named business point as a graph frontier, not as a request for nearby lines. The evidence reader will
  supply complete enclosing function bodies for exact hits. Expand the frontier in this order:
  1. the exact definition and every real entry/caller;
  2. decision branches and important callees inside that definition;
  3. the primary object's producer and first repository boundary before the read;
  4. transformations, state mutation, transaction/persistence, and cleanup;
  5. downstream readers, emitted events, responses, and final business consumers.
  Keep one end-to-end business goal connected across these layers.
- Classify every newly found boundary before adding it: same call, direct async continuation, later independent trigger,
  or merely related code. Search direct calls/event publication to prove causality. A later HTTP reader or separate job is
  not the next runtime step; plan it as a separate flow only when requested, otherwise collect it as a downstream consumer.
- A separately arriving stop/cancel request needs its own route/command entry query plus the shared sequence/state mutation.
  For a claimed runtime/domain event, search its constructor/emitter and persistence boundary; the controller call site or
  a similarly named log line is not enough. For boolean gates, search the complete helper definition and every call site.

- Related query/start/execute/settle/respond stages should be planned as one complete business flow, not independent flows.
- For a refinement, prioritize exact unresolved symbols named in current_report_context before broader evidence requested by

- Do not produce the final report and do not invent source paths absent from repository_path_index.
