Rules:
- Include every existing unknown exactly once and copy its question text exactly.
- Use confirmed or disproved only when the numbered source evidence directly supports the conclusion and file/line/symbol
  identify that evidence. Otherwise use unresolved and leave file empty with line 1.
- A search miss is not proof of absence. Do not remove an unknown merely because a query returned no match.
- Resolve data-origin gaps by following the producer before the first in-flow read and the consumer after each write.
  A repository getter, DTO, or table read is not by itself proof of where the business data originally came from.
- When evidence finds the real trigger registration/caller, replace entry_source. Do not claim that a detached resolution
  node has become a flow step; if the existing first step still omits the entry, keep that structural gap unresolved so a
  complete report refinement can rebuild the flow.
- Treat grouped control-flow evidence as one path: distinguish a state that is explicitly changed, cleaned by defer,
  unchanged because an early return skips later code, and not created because registration occurs later. An application
  log is not a runtime/domain event. Apply step_updates when a resolved unknown changes what a flow step should show.
- Keep conclusions concise and use the language required by OUTPUT LANGUAGE. Do not add speculative flow updates.
- data_origins, data_flow, and consumer_targets are complete-array replacements, never a side-branch patch. Only return
  a field when the replacement preserves the existing producer-to-consumer main chain and adds or corrects evidence; a reward,
  notification, or milestone subflow must not replace the primary data lineage.
- This stage converges existing questions; it does not broaden the analysis. Keep new_unknowns empty unless new source
  evidence both resolves an existing question and exposes one different material gap. Never paraphrase an unresolved
  question into new_unknowns, and never add a fact already proven by current data_origins or data_flow.
- Each unresolved question is one atomic fact. Never keep a broad question that also lists outcomes already confirmed by
  state_effects. If evidence proves the asked fact, resolve it and update affected flow/step text so no stale contradiction
  remains; if evidence proves only a different fact, leave the exact question unresolved without speculative updates.
- current_report_context includes the complete reader overview. When a resolved fact changes or contradicts the plain story,
  actor entry, domain relationship, term, or business object, return an overview_update with a complete replacement for each
  affected array and/or the affected object update. A confirmed fact must not leave stale “未证明/未展示/待确认” text in any
  overview field. When a step update relies on a newly resolved source, set source_question so the plugin can attach that
  exact clickable node.
- Before returning, audit every named state/event in analysis_focus against the affected failure step. Do not omit the event
  outcome just to keep state_effects short; use event_not_emitted when the source proves an early return before construction.
- For an unresolved question, return next_frontier_queries only when this batch's numbered source literally exposes a new
  direct caller, callee, event, table, or state identifier that can advance that exact question. Do not choose a symbol
  merely because it appears elsewhere in the report. Return no frontier when the evidence exposes no causal next hop.
